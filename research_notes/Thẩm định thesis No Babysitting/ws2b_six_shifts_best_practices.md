# WS2b — Anthropic's "Six Shifts" and evidence-backed best practices for applying AI (design lens for No Babysitting)

Research date: 2026-11-17. Scope: Six Shifts source and meaning; mapping to NB gaps, capabilities, and evaluation dimensions; vendor guidance (Anthropic, OpenAI, Google); research on effective vs. ineffective AI users and on training. Per the brief, the Six Shifts background claims (e.g., the "80% system prompt removed" figure) were **not** verified. They are quoted only as context.

Tag legend: [Fact] = stated by a primary source · [Finding] = empirical research result · [Inference] = my reasoning from cited material · [Hypothesis] = a proposal to test.

## Q1. What is the official source for "Six Shifts", and what exactly does each shift say?

### Takeaway
"Six Shifts" is the informal name for the then→now table in Anthropic's engineering post **"The new rules of context engineering for Claude 5 generation models"** by Thariq Shihipar (Member of Technical Staff, Anthropic), published **July 24, 2026**. The post is about configuring **Claude Code and agent harnesses** (system prompts, CLAUDE.md, skills, tool descriptions). It does not address knowledge workers applying AI. So using it as NB's design lens means translating it from "how you configure the agent" to "how a person frames and runs work with AI".

**Six Shifts summary table (source: Shihipar, "The new rules of context engineering for Claude 5 generation models", Anthropic, 2026-07-24, [link](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/))**

| # | Then → Now (primary wording) | What the post says (quoted/close paraphrase) |
|---|---|---|
| 1 | **Give Claude rules → Let Claude use judgement** | "newer models have better judgement and can handle these decisions well without explicit rules." A ban like "default to writing no comments" became "Write code that reads like the surrounding code: match its comment density, naming, and idiom." Keep constraints for "highly important areas" ("Avoid making them overconstrained, except in highly important areas"). Conflicting rules like "leave documentation as appropriate" vs "DO NOT add comments" show up in transcripts. |
| 2 | **Give Claude examples → Design interfaces** | "giving examples actually constrains them to a certain exploration space… Instead of using examples, think more about the design of your tools, scripts and files — what parameters does Claude have and how can they be more expressive?" Example: a status enum (pending / in_progress / completed) plus one rule ("only one task in_progress at a time") replaced a ~9,100-character TodoWrite description. |
| 3 | **Put it all upfront → Use progressive disclosure** | "Claude Code has gotten very competent at using progressive disclosure — loading the right context at the right times." It is "a common myth" that CLAUDE.md or skills should be "a central repository for every known practice". Use a tree of files loaded at the right time. Code review and verification moved into skills; some tools load lazily via ToolSearch. |
| 4 | **Repeat yourself → Simple tool descriptions** | "We found we could delete these repeat examples and put instructions on how to use tools in the tool descriptions rather than the system prompt." |
| 5 | **Memory in CLAUDE.md files → Auto-memory** | "We used to encourage users to save things to Claude's memory, by using the # hotkey… Instead, Claude now automatically saves memories that are relevant to the work and to you." |
| 6 | **Simple specs → Rich references** | "Claude can handle increasingly more complicated references." A spec can be an HTML mockup, "a detailed test suite, or a function in a different codebase that Claude might port." "Rubrics allow Claude to try and verify your taste in a particular field (e.g. what does a good API design look like) by using dynamic workflows and spinning up verifier agents with those rubrics." |

All quotes above are from the [primary post](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/).

- [Fact] "What still matters" in the post: keep CLAUDE.md lightweight (what the repo is for, mostly gotchas, skip anything Claude can read from the repo); treat skills as lightweight guides for team- or product-specific opinions; prefer code-based references (an HTML mockup beats a written description or a screenshot); audit regularly and simplify (the post points to `claude doctor` / `/doctor`) — [primary post](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)

**Companion source the post points to: "Field Guide to Fable" (Thariq Shihipar, AI Engineer World's Fair, 2026-07-01)**
- [Fact] The post's conclusion sends readers to a "Fable field guide" for prompting more advanced models — [primary post](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/). - [Fact, transcript] "Capability overhang": the gap between what a model can do and what people get out of it. "What contains them is us." "We tried to give it context and not just constraints." — [conffab](https://agents.conffab.com/worlds-fair/live/day-1-keynotes/sessions/1782921900.md)
- [Fact, transcript] An "unknowns" matrix for prompting: known knowns (what you write in the prompt), known unknowns ("What haven't I figured out yet?"), unknown knowns ("What's so obvious I'd never write it down?"), unknown unknowns ("What haven't I considered at all?"). Suggested techniques: a blind-spot pass, interviews where Claude asks the questions that would change the architecture, references, prototypes ("4 wildly different design directions so I can react to them"), and implementation notes that log deviations from the plan — [conffab](https://agents.conffab.com/worlds-fair/live/day-1-keynotes/sessions/1782921900.md)
- [Fact, transcript] "The most important part of working with Fable is staying in the loop." He suggests having Claude quiz you on what it did so you can understand and defend the work — [conffab](https://agents.conffab.com/worlds-fair/live/day-1-keynotes/sessions/1782921900.md)

**Adjacent official Anthropic framework: AI Fluency "4D"**
- [Fact] *The AI Fluency Framework* (© 2025 Rick Dakan, Joseph Feller, and Anthropic; CC BY-NC-SA 4.0) defines four competencies. **Delegation** — "Setting goals and deciding whether, when and how to engage with AI." **Description** — "Effectively describing goals to prompt useful AI behaviors and outputs." **Discernment** — "Accurately assessing the usefulness of AI outputs and behaviors." **Diligence** — "Taking responsibility for what we do with AI and how we do it." It also defines three modes: Automation, Augmentation ("thinking partner"), and Agency ("configure AI to independently perform future tasks") — [Anthropic AI Fluency Framework PDF](https://www-cdn.anthropic.com/b383cf6baddbfc72fdf8b0ed533a518e2872d531.pdf)

### Inferences
- [Inference] Six Shifts is written for whoever configures the agent's context (harness or CLAUDE.md authors). Its implicit thesis is "trust model judgment more and steer it through intent, structure, and references rather than rules and samples." For NB, the useful translation is: **a knowledge worker's prompt or brief plays the same role as a system prompt**, so the same over-constraining failure modes probably apply to how people brief AI. That transfer is plausible but **not demonstrated** for non-coding work.
- [Inference] Six Shifts is about the *AI side* of the collaboration, i.e. how to set up context. The human-side content that NB most needs is in the companion Field Guide (unknowns, staying in the loop, quizzing yourself) and in the AI Fluency 4D framework (Delegation / Description / Discernment / Diligence). NB's "methodology lens" should therefore be **Six Shifts + Field Guide + 4D**, not Six Shifts alone.
- [Inference] The shifts depend on the model generation ("for Claude 5 generation models"). That means any NB guidance derived from them will need re-checking when models change. The post itself says to keep auditing and simplifying.

### Gaps
- I could not confirm that claude.dev is formally operated by Anthropic beyond the 308 redirect from claude.com and the author's Anthropic byline.
- I found no Anthropic-authored written version of the "Field Guide to Fable" talk. The talk content above rests on a third-party transcript summary.
- The post publishes no evaluation of the shifts on non-coding work or with non-developer users.

## Q2. What does each shift imply for a knowledge worker, and how does it map onto NB's gaps, capabilities, and evaluation dimensions? Where is Six Shifts clear, and where is it silent?

### Takeaway
Shift 6 (rich references and rubrics) and shift 3 (progressive disclosure) give the clearest, most usable direction for NB: framing, acceptance criteria, staged discovery, and verification. Shift 1 (judgment over rules) is a strong philosophy but sits in tension with the evidence on over-reliance and the "jagged frontier". Shifts 4 and 5 are mostly harness hygiene that platforms already absorb. Six Shifts says nothing on problem discovery, human verification and over-reliance, skill development, when *not* to use AI, and non-technical users, and these are NB's core.

### Cited Findings
- [Fact] Each shift's content: see the table in Q1 — [primary post](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)
- [Fact] Anthropic's own prompting docs still say "Examples are one of the most reliable ways to steer Claude's output format, tone, and structure… Include 3–5 examples for best results." So shift 2 is scoped to tool and interface design, not a general ban on examples — [Anthropic, Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Fact] Google's Gemini guidance: "We recommend to always include few-shot examples in your prompts… Prompts without few-shot examples are likely to be less effective." This directly contrasts with shift 2 as worded — [Google AI Studio, Prompt design strategies](https://aistudio.google.com/docs/prompting-strategies)
- [Fact] OpenAI's GPT-5 guide: "contradictory or vague instructions can be more damaging to GPT-5 than to other models", and removing contradictions "drastically streamlined and improved" performance. This supports shifts 1 and 4 — [OpenAI GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide.md)
- [Finding] Outside the AI capability frontier, consultants using GPT-4 were **19 percentage points less likely** to reach correct solutions (control ≈84.5% correct vs 60–70% in the AI arms). This cautions against "let the AI use judgment" when the task is outside the frontier — [Dell'Acqua et al., HBS WP 24-013 (2023); Organization Science 2026](https://mitsloan.mit.edu/sites/default/files/2023-10/SSRN-id4573321.pdf)
- [Finding] In the AI Fluency Index, users who produced **artifacts** were more directive but less evaluative: identifying missing context fell 5.2 pp, fact-checking 3.7 pp, and questioning reasoning 3.1 pp. Polished, rich outputs reduce scrutiny — [Anthropic AI Fluency Index, 2026-02-23](https://academy.claude.com/tutorials/the-ai-fluency-index)
- [Finding] Higher confidence in GenAI is associated with less critical thinking, and higher self-confidence with more. With GenAI, critical thinking shifts toward "information verification, response integration, and task stewardship" (survey, n=319, 936 examples) — [Lee et al., CHI 2025](https://consensus.app/papers/details/w:162fef2e-deec-4ea1-a502-c3474d16fce2/?utm_source=claude_desktop)

- Whether the problem itself is the right one (problem discovery): absent from the post. - When not to use AI (the jagged frontier): absent — [Dell'Acqua et al.](https://mitsloan.mit.edu/sites/default/files/2023-10/SSRN-id4573321.pdf)
- Human verification and over-reliance: absent. The post's verification is *model-side* (verifier agents). For the human side, see 4D **Discernment** and **Diligence**, and [Buçinca et al. 2021](https://consensus.app/papers/details/w:73713e06-5efc-4c9b-b0da-7408bdb871aa/?utm_source=claude_desktop)
- Skill development and deskilling: absent — see [Shen & Tamkin 2026](https://www.anthropic.com/research/AI-assistance-coding-skills) and [Bastani et al., PNAS 2025](https://papers.ssrn.com/abstract=4895486)
- Success measure: the post's evidence is "coding evaluations" (model task performance). It does not measure human outcomes, collaboration quality, or capability — [primary post](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)

### Inferences
- [Inference] Of NB's four evaluation dimensions, Six Shifts speaks to **Task Outcome** (via shift 6 rubrics and verifiers) and loosely to **Problem Framing** (shifts 1, 3, 6). It has nothing on **User Capability Development**, and on **Human-AI Collaboration** it only speaks indirectly (over-constraining). NB's two most distinctive dimensions therefore need grounding outside Six Shifts.
- [Inference] The core philosophical tension for NB: Six Shifts says "trust the model's judgment more", while the human-factors evidence says "people already trust it too much, especially when output looks polished" (Lee et al.; Fluency Index artifact effect; BCG outside-frontier result). A coherent NB stance is **"give the AI more latitude on *how*; keep the human firmly in charge of *what*, *whether*, and *is it good*"**. That keeps Six Shifts on the AI-configuration side and puts 4D Delegation and Discernment on the human side.
- [Inference] Shifts 4 and 5 describe things platforms are already automating (`/doctor`, auto-memory). NB should not build features around them, beyond lightweight "review what was remembered" and "audit for contradictory instructions" prompts. This is consistent with B6 and B8.
- [Hypothesis] The highest-leverage NB behavior derived from Six Shifts is a **"reference + rubric before execution"** step: the user brings a real example, source, or prior artifact; NB helps turn "good" into 3–7 checkable criteria; execution happens natively; then a verification pass compares the output against the rubric, with a human discernment checkpoint. This maps onto Problem Framing, Evaluation, and Task Outcome at once, and it can be tested without persistent memory (answers T2).

### Gaps
- No evidence that the shifts improve outcomes when *humans* brief AI for non-coding work. The transfer is an inference.
- Six Shifts gives no criterion for deciding which areas are "highly important" enough to keep rules. NB would need its own risk heuristic (vendor reversibility rules are the best available proxy; see Q3).

## Q3. What do the major vendors and credible research recommend, which practices have the strongest evidence, and where do they reinforce, extend, or contradict Six Shifts?

### Takeaway
Vendor guidance converges on five things: clear intent with context and rationale; minimal, non-contradictory instructions; just-in-time context; verifiable targets (tests and rubrics); and reversibility-based human checkpoints. The strongest *independent* evidence, though, is about the human side: task-AI fit (the jagged frontier), active verification and cognitive forcing against over-reliance, and how people engage with AI. Vendor practices rest mostly on internal evals and engineering experience rather than outcome RCTs with knowledge workers.

### Cited Findings
**Anthropic**
- [Fact] "Think of Claude as a brilliant but new employee who lacks context on your norms and workflows… **Key test:** Show your prompt to a colleague with minimal context… If they'd be confused, Claude will be too." — [Anthropic, Prompting best practices (covers Claude 5.x and Opus 5.5)](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Fact] "Providing context or motivation behind your instructions, such as explaining to Claude why such behavior is important… Claude can generalize from the explanation." (Example: "NEVER use ellipses" vs. an explanation that the text-to-speech engine can't pronounce them.) This reinforces shift 1 — [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Fact] On aggressive language: replace "CRITICAL: You MUST use this tool when…" with "Use this tool when…", because newer models over-trigger. This reinforces shift 1 — [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Fact] Self-check: "Before you finish, verify your answer against [test criteria]" — "catches errors reliably". But Claude Opus 5 "verifies its own work well without explicit instruction", and carried-over verification instructions "can cause over-verification". Model-side verification is being absorbed into the model — [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Fact] Long-horizon agentic work: write tests first and track them in structured form (tests.json); use git and progress files for state; "Provide verification tools… Claude needs to verify correctness without continuous human feedback." — [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Fact] Autonomy vs. safety: "take local, reversible actions like editing files or running tests, but for actions that are hard to reverse, affect shared systems, or could be destructive, ask the user before proceeding." For payments: "have a person approve each call to any tool that can move money." — [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Fact] "Tests are there to verify correctness, not to define the solution"; models can over-focus on passing tests or hard-coding. This is a Goodhart warning relevant to rubric-based evaluation — [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Fact] Context engineering: "good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome". It describes "context rot", the "Goldilocks zone" between brittle hard-coded logic and vague guidance, just-in-time retrieval, compaction, structured note-taking, and sub-agents — [Anthropic Engineering, "Effective context engineering for AI agents" (Sep 2025)](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). Excerpts were seen via search snippets only, not a full fetch. The date is from prior knowledge, not re-verified this session.
- [Fact, prior knowledge — not re-fetched this session] "Building effective agents" (Schluntz & Zhang, Dec 2024) advises starting with the simplest solution and adding complexity (workflows → agents) only when needed; lists evaluator–optimizer loops; and says agents should get "ground truth from the environment" at each step, with checkpoints for human feedback — [Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents). "Claude Code best practices" (Apr 2025) recommends explore → plan → code → commit, giving Claude a verifiable target (tests, visual mocks), being specific, and course-correcting early — [Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-best-practices)

**OpenAI**
- [Fact] GPT-5 guide on "agentic eagerness": for low eagerness, "Get enough context fast… stop as soon as you can act", or fixed tool-call budgets. For high eagerness, "keep going until the user's query is completely resolved" and "Do not ask the human to confirm or clarify assumptions". Uncertainty thresholds should depend on risk, e.g. checkout and payment tools get "a lower uncertainty threshold for requiring user clarification" than search — [OpenAI Cookbook, GPT-5 prompting guide (now marked archived)](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide.md)
- [Fact] Tool preambles (rephrasing the user's goal, then giving a plan and progress updates) are recommended. Contradictory instructions "can be more damaging to GPT-5 than to other models". A self-built "rubric that has 5-7 categories" is used for zero-to-one quality — [OpenAI GPT-5 guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide.md)
- [Fact] There are newer model-specific guides (GPT-5.1, Nov 13, 2025; later GPT-5.5), and OpenAI says old prompts should not be dropped in unchanged on newer models. This is the same "re-baseline per generation" message as Six Shifts — [OpenAI GPT-5.1 guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5-1_prompting_guide); [The Decoder on GPT-5.5](https://the-decoder.com/openai-says-old-prompts-are-holding-gpt-5-5-back-and-developers-need-a-fresh-baseline/) (secondary)

**Google**
- [Fact] Gemini guidance: "clear and specific instructions", specify constraints and format, add context "instead of assuming that the model has all of the required information", and "always include few-shot examples". For Gemini 3: be "direct, well-structured, and clearly define the task and any constraints"; avoid "unnecessary or overly persuasive language". The agentic template includes planning before acting, self-critique ("Review your output against the user's task"), persistence, and risk assessment that "distinguishes between low-risk exploratory actions (reads) and high-risk state changes (writes)" — [Google AI Studio, Prompt design strategies (no date on page; mentions Gemini 3 / 3.6+ / 4)](https://aistudio.google.com/docs/prompting-strategies)

**Independent research (human side)**
- [Finding] Preregistered field experiment, n=758 BCG consultants: on 18 tasks inside the frontier, AI users completed 12.2% more tasks, 25.1% faster, with >40% higher quality. Below-average performers improved 43% and above-average 17%. On the outside-frontier task, AI users were 19 pp less likely to be correct. "Centaurs" divide tasks between human and AI; "Cyborgs" integrate continuously — [Dell'Acqua et al.](https://mitsloan.mit.edu/sites/default/files/2023-10/SSRN-id4573321.pdf); published in [Organization Science 2026](https://consensus.app/papers/details/w:88d7dd57-8222-4123-87a8-83526b351bfb/?utm_source=claude_desktop)
- [Finding] Cognitive forcing interventions (n=199) significantly reduced over-reliance compared with simple explanations. Explanations alone did not reduce over-reliance and may increase it. Trade-off: users rated the most effective designs least favorably, and the benefits went mostly to people high in Need for Cognition — [Buçinca et al., CSCW 2021](https://consensus.app/papers/details/w:73713e06-5efc-4c9b-b0da-7408bdb871aa/?utm_source=claude_desktop)
- [Finding] For AI-generated *plans* (agentic workflows), an "Assumption" cognitive forcing function (analyzing the plan's assumptions) reduced over-reliance most without raising cognitive load. Users found "WhatIf" most helpful (controlled experiment; preprint) — [Ghosh et al., 2026, arXiv](https://consensus.app/papers/details/w:30026832-d716-4f1e-aea9-92fee8fa6b3d/?utm_source=claude_desktop)
- [Finding] A systematic review of automation bias (35 studies, 2015–2025): explanations and transparency are often insufficient; "user engagement emerges as the most feasible and impactful point of intervention"; more verification effort reduces complacency — [Romeo et al., AI & Society 2025](https://consensus.app/papers/details/w:94f2b33c-1128-4177-bf58-12774ee7564d/?utm_source=claude_desktop)
- [Finding] Experienced open-source developers (n=16, 246 real tasks, RCT) were **19% slower** with AI. They had forecast 24% faster and afterwards believed they were 20% faster. Self-reported productivity is unreliable — [METR study coverage, The Register, 2025-07-11](https://www.theregister.com/2025/07/11/ai_code_tools_slow_down/); see also [Zvi's analysis](https://thezvi.substack.com/p/on-metrs-ai-coding-rct) for critiques (one outlier was 38% faster; critics say it does not generalize to experienced AI-tool users)
- [Finding] GenAI's quality effect depends on the task: in a lab-in-the-field RCT (n=128 knowledge workers), quality rose for knowledge packaging and creation but **fell for knowledge acquisition** — [Bottesch et al., 2026, arXiv](https://consensus.app/papers/details/w:1e089224-b0a2-428d-afb0-05bc4ee11b1d/?utm_source=claude_desktop)

### Inferences
- [Inference] Vendor practices aimed at the *model* (self-check, verification prompts, long-context ordering, tool descriptions) are being **absorbed into models and harnesses generation by generation**. Anthropic now tells users to *remove* verification instructions on Opus 5, and OpenAI says to re-baseline prompts for each model. Prompt-technique coaching is therefore a depreciating asset. Human-side practices (task–AI fit judgment, framing, discernment, responsibility) do not depreciate this way.
- [Inference] Everyone converges on risk- and reversibility-based autonomy (Anthropic, OpenAI, Google). That is external support for NB's B5 risk-tiered adaptation. NB can use the vendors' "reads vs writes" and "reversible vs shared/destructive" rules as its starting heuristic instead of inventing one.
- [Inference] Cognitive forcing works but is disliked (Buçinca). That is a direct UX risk for NB's "coaching friction > benefit" kill criterion. Light-touch forcing functions (an assumption check on the AI's plan) look like the best effort-to-effect ratio (Ghosh et al.).

### Gaps
- Few independent RCTs test vendor prompting practices (intent statements, acceptance criteria, rich references) on knowledge-worker *outcomes*. Most evidence comes from vendor internal evals or engineering experience.

- I did not review OpenAI's "A practical guide to building agents" or Google's agent-specific guides in this pass.

## Q4. What evidence distinguishes effective from ineffective AI users, and does training or coaching improve outcomes?

### Takeaway
Effective users **engage**: they iterate, question, verify, and use AI to build understanding rather than to substitute for thinking. They also judge task–AI fit. Ineffective users accept first or polished outputs and offload core thinking, which feels equally productive in the moment. Training effects are **mixed and depend on what is trained**. Brief, targeted training and cognitive scaffolding have improved outcomes in several RCTs. Generic prompt-engineering instruction made people *worse* outside the frontier in the BCG study, and rigid behavioral protocols hurt in a Fortune 500 field experiment.

### Cited Findings
**What distinguishes effective users**
- [Finding] AI Fluency Index (Anthropic, 2026-02-23; 9,830 Claude.ai conversations from Jan 20–26, 2026; 11 of 24 4D behaviors observable). Prevalence: iterates and refines 85.7%; clarifies goal 51.1%; provides examples 41.1%; specifies format 30%; sets interaction mode 30%; tone 22.7%; identifies missing context 20.3%; defines audience 17.6%; questions reasoning 15.8%; consults on approach before execution 10.1%; **checks facts 8.7%**. Iterative conversations showed 2.67 vs 1.33 fluency behaviors, with users 5.6× more likely to question reasoning and 4× more likely to flag missing context. Limitations: correlational, early-adopter skew, binary classifiers — [Anthropic AI Fluency Index (Swanson, Bent, Ludwig, Dakan, Feller)](https://academy.claude.com/tutorials/the-ai-fluency-index)
- [Finding] RCT (Anthropic Fellows, n=52, mostly junior engineers learning the Trio library): the AI group scored 50% vs 67% on a follow-up quiz, with the biggest gap on debugging, and the speed gain was not significant. Heavy-delegation patterns averaged <40%. Higher scorers used AI for explanations, follow-up and conceptual questions while coding themselves. Pattern subgroups were small (some n≈4) — [Shen & Tamkin, Anthropic, 2026-01-29](https://www.anthropic.com/research/AI-assistance-coding-skills); [arXiv 2601.20245](https://www.arxiv.org/pdf/2601.20245)
- [Finding] A field experiment with ~1,000 high-school students: unrestricted GPT-4 ("GPT Base") raised practice performance by 48% but lowered exam performance by **17%** versus no access. A guarded tutor ("GPT Tutor", +127% in practice) avoided the harm. Logs show GPT Base users mostly asked for answers ("crutch") — [Bastani et al., PNAS 2025, 122:e2422633122](https://papers.ssrn.com/abstract=4895486); [Wharton summary](https://knowledge.wharton.upenn.edu/article/without-guardrails-generative-ai-can-harm-education/)
- [Finding] RCT with early-career knowledge-worker analogs: gains from GenAI were not predicted by GPA or prior knowledge but by **"AI Interaction Competence" — the ability to elicit, filter, and verify model outputs**. Low-AIC users saw limited or even negative returns. A scaffolding intervention (concept maps) reduced outcome variance (preprint) — [Idan et al., 2026, arXiv](https://consensus.app/papers/details/w:c117aecd-7ddd-4f8c-90ba-b10c7a577873/?utm_source=claude_desktop)
- [Finding] A three-wave survey (n=589 students and early-career knowledge workers): *dependent* offloading (delegating core thinking) correlated with cognitive-agency transfer and lower intrinsic motivation; *autonomous* offloading (AI as scaffold) correlated with better perceived outcomes. **Both gave comparable immediate benefits**, so maladaptive use is "difficult for users to detect from immediate experience" — [Zhu et al., Frontiers in Psychology 2026](https://consensus.app/papers/details/w:b7629dc3-4f13-43af-a025-88bcf034c246/?utm_source=claude_desktop)
- [Finding] Four experiments (N=3,562): GenAI collaboration raised immediate performance, but the gain did not carry over to later solo tasks, and moving to solo work lowered intrinsic motivation — [Wu et al., Scientific Reports 2025](https://consensus.app/papers/details/w:95c1638c-2304-4b3d-a8b2-60ccb6c3f6c1/?utm_source=claude_desktop)
- [Finding] Gains on in-frontier tasks are largest for less experienced or lower-skilled workers: customer support +14% overall, biggest for novices (n=5,179) — [Brynjolfsson et al., QJE](https://consensus.app/papers/details/w:8b15b736-c612-457f-b2dc-26ae23406589/?utm_source=claude_desktop); professional writing −40% time, +18% quality, with inequality reduced (n=453) — [Noy & Zhang, Science 2023](https://consensus.app/papers/details/w:2a338923-aa77-4efb-ba2d-74d892eafb46/?utm_source=claude_desktop); developers +26% tasks, larger for less experienced (n=4,867) — [Cui et al., Management Science 2026](https://consensus.app/papers/details/w:6d3950b2-aeb8-4959-ad21-3b39fe1ee011/?utm_source=claude_desktop)

**Does training or coaching help?**
- [Finding] **Negative case:** in the BCG experiment, the "GPT + prompt engineering overview" arm (instructional videos and documents) did **worse** on the outside-frontier task than GPT-only: −24 pp vs −13 pp relative to control, with the difference significant at the 10% level — [Dell'Acqua et al., HBS WP 24-013, pp. on Table 4](https://mitsloan.mit.edu/sites/default/files/2023-10/SSRN-id4573321.pdf)
- [Finding] **Positive case:** law-student RCT (n=164). Untrained LLM access was counterproductive (shorter answers, more case misstatements). Brief training raised adoption (41% vs 26%) and scores (+0.27 grade points, p=0.027), mainly by increasing adoption. Without training, higher-ability students opted out while lower-ability students adopted unproductively (preprint) — [Chen et al., 2026, arXiv](https://consensus.app/papers/details/w:e6c19f0a-1909-4c90-ac13-502e3462316e/?utm_source=claude_desktop)
- [Finding] **Positive case:** cross-country experiment (n=150): unguided AI use produced cognitive offloading with no gain in reasoning quality, while **structured prompting** reduced offloading and improved critical reasoning on expert rubrics — [Gerlich, Data 2025](https://consensus.app/papers/details/w:63f899c9-29dc-4c9c-9704-4174c40f8a73/?utm_source=claude_desktop)
- [Finding] **Mixed case:** Fortune 500 retailer field experiment (n=388). A *behavioral* scaffold (a rigid protocol of joint AI use in pairs) **lowered** document quality and output. A *cognitive* scaffold (training that reframed AI as a thought partner) raised quality at the top of the distribution. Design confounds noted (session-time confound, attrition, LLM grading sensitive to length) — [Farach et al., 2026, arXiv](https://consensus.app/papers/details/w:ad0f6b0f-b9e2-4966-bd80-074f8e21480f/?utm_source=claude_desktop)
- [Finding] Over-reliance interventions such as cognitive forcing work but are disliked and benefit high-Need-for-Cognition users most — [Buçinca et al. 2021](https://consensus.app/papers/details/w:73713e06-5efc-4c9b-b0da-7408bdb871aa/?utm_source=claude_desktop)

### Inferences
- [Inference] The evidence supports NB's premise that *how* people use AI matters a lot: the AIC predictor, the dependent vs autonomous offloading split, and the iteration correlation all point that way. It also shows the risk that **naïve coaching makes people worse** (BCG prompt overview, the Farach behavioral protocol). NB's coaching must target **calibration** (task–AI fit, verification, assumption-checking) rather than prompt technique. Technique is also the part platforms absorb fastest.
- [Inference] Harmful use "feels" as productive as healthy use (Zhu; METR). That strengthens the case for NB's Evaluation & Learning capability. It also means **users may not perceive NB's value** in the moment, which bears on the counter-thesis "users want results, not better collaboration skills" and argues for leading with outcome value rather than skill-building.
- [Inference] The 4D framework (Delegation / Description / Discernment / Diligence) maps cleanly onto NB's capabilities: Delegation ≈ Problem Discovery & Framing and Workflow Design; Description ≈ Coaching on framing; Discernment ≈ Evaluation; Diligence ≈ ownership and responsibility. Anthropic has already put it into an observational index (11 behaviors). NB could reuse those observable behaviors as Human-AI Collaboration indicators rather than inventing a scale. This fits B4's "no universal proficiency scale" if the behaviors are used as signals, not a score.
- [Hypothesis] The behaviors least present in the Fluency Index — "checks facts" (8.7%), "consults on approach before execution" (10.1%), "questions reasoning" (15.8%) — are the most promising, measurable targets for NB's first experiment, because they have the most room to move and the clearest link to outcome risk.

### Gaps
- No RCT found that tests a *coaching layer* like NB (adaptive, problem-to-outcome) against plain platform use for professional knowledge workers. The closest are training RCTs with students or law students and one Fortune 500 field experiment with confounds.
- Several key training studies (Chen et al.; Idan et al.; Farach et al.; Ghosh et al.) are 2026 preprints and not yet peer reviewed.
- The METR figures come from press coverage and an analysis post; the METR paper itself was not fetched this session.
- I did not verify the P&G "Cybernetic Teammate" field experiment (Dell'Acqua et al., 2025) or Microsoft Copilot field studies in this pass, so they are omitted rather than cited.
